I think this is the right time to pause and consolidate. We've made a lot of architectural decisions, and the vision has evolved significantly from "AI second brain" into something much more specific.

This is my current understanding of **Et Al — Personal Operating System**.

# Et Al — Personal Operating System

## One Sentence Definition

> **Et Al is an MCP-native Personal Operating System that becomes the source of truth for a person's life, allowing any AI agent to understand, reason about, and help execute their goals through a continuously evolving knowledge, project, and action graph.**

---

# The Core Philosophy

Most productivity tools treat information as something to store.

Et Al treats information as something that should **compound into action**.

The system is built around this lifecycle:

```
Capture
   ↓
Understand
   ↓
Organize
   ↓
Execute
   ↓
Reflect
   ↓
Create
   ↓
Grow
```

The goal is not to collect notes.

The goal is:

> "Never lose important information, never forget important commitments, and always know what to do next."

---

# The Most Important Architectural Decision

# 1. Workspace System

## Definition

A Workspace is a **context boundary**.

It represents an area of life, project, responsibility, or pursuit.

Everything happens inside a Workspace.

---

## Workspace hierarchy is a strict tree.

One parent only.

Example:

```
Life

├── School
│
│   ├── CS180
│   ├── Math 115A
│   └── AI Club
│
├── Career
│
│   ├── Internship Search
│   └── Portfolio
│
├── Health
│
│   ├── Fitness
│   └── Nutrition
│
└── Build

    ├── Et Al
    ├── LEXI
    └── Other Projects
```

---

## Why strict hierarchy?

Because Workspace is also the default AI context.

If you enter:

```
Life → Build → Et Al
```

the AI knows:

Primary context:

* Et Al

Inherited context:

* Build
* Life

# 2. Objectives

They answer:

> "Why does this work matter?"

Example:

```

Launch MVP

    ↓

Build Authentication

Build Knowledge Engine

Build MCP Server

    ↓

Tasks:

Implement OAuth

Create User Model

Create API Routes
```

---

# 3. Tasks

Tasks are execution units.

Tasks answer:

> "What specific action needs to happen?"

Tasks can be:

* created manually
* generated by AI
* expanded from objectives

Example:

Human:

> "Build authentication"

AI:

```
Authentication

├── Create user schema

├── Add login flow

├── Add OAuth

└── Add session handling
```

---

# 4. Daily 3 System

This is one of Et Al's defining features.

The philosophy:

> Low volume, high commitment.

The user does not manage a giant daily todo list.

Every day:

Exactly 3 meaningful tasks.

---

## Daily 3 Flow

Morning:

```
Planning Engine

↓

Analyzes:

- Workspace priorities
- Objective priorities
- Deadlines
- Dependencies
- Workspace Health
- Existing tasks
- Momentum

↓

Suggests 3 tasks

↓

User reviews

↓

User swaps if needed

↓

Confirm

↓

Locked for today
```

---

## Important:

Daily 3 does NOT refresh when tasks are completed.

Example:

You finish all 3 at noon.

You do not get 3 more.

The point is commitment.

Tomorrow is a new set.

---

## Daily 3 Tracks:

* completion
* streak
* consistency
* reflections

Example:

```
Health
██░░░░░░░░ 20%

█░░░░░░░░░ 10%
```

Instead of:

Choose:

* 1 Et Al task

Because neglected areas matter.

Not silent modification.

AI proposes changes.

The system applies controlled changes.

Git-style.

Example:

```

from Supabase to Cloudflare D1.

Reason:

...

Apply Patch?

[Accept]

[Reject]
```

# The Final Identity of Et Al

I think the final definition is:

> **Et Al is an MCP-native Personal Operating System that acts as the source of truth for your life. # Remaining things we still need to design before writing docs

I think we are ~80% there.

The remaining major design questions:

1. **Exact data model**

   * How tables/entities relate.

2. **MCP tool specification**

   * What capabilities Et Al exposes.

3. **Context Engine algorithm**

   * How it decides what information enters context.

4. **AI approval workflows**

   * How suggestions become changes.

5. **Knowledge graph implementation**

   * How Insights and Relationships are stored.

6. **Workspace Health calculation**

   * How the OS determines life balance.

7. **Versioning system**

   * Documents, decisions, AI patches.

8. **Web app UI details**

   * Exact pages/components.

Once we solve those, I think we can confidently generate the documentation set. I would not write the docs before those are settled because these decisions are essentially the "constitution" of the OS.
